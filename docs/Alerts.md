# Оповещения

Узел сам сообщает об отказах письмом. Настройка сводится к двум шагам: указать адреса и один раз завести ящик отправителя.

## Настройка

### Получатели

В `config.json`:

```json
"alerts": {
  "to": ["ivanov@example.ru", "petrov@example.ru"]
}
```

### Отправитель

Скопируйте `mail_account.json.example` в `~/.every_camera/mail_account.json` и заполните:

```json
{
  "preset": "yandex",
  "user": "obs-alerts@yandex.ru",
  "password": "пароль приложения",
  "from": "obs-alerts@yandex.ru"
}
```

Сервер, порт и шифрование подставляются по имени провайдера: `yandex`, `mailru`, `gmail`, `brevo`, `resend`, `localhost` или `custom`. Для `custom` укажите `host`, `port` и `security`.

Файл ищется по порядку:

| Где | Зачем |
|---|---|
| `~/.every_camera/mail_account.json` | обычное место, вне рабочей копии |
| `mail_account.json` рядом с программой | как `env.sh` |
| `alerts.smtp` в `config.json` | если узлу нужен свой ящик |

Оба файла в `.gitignore`, пароль не попадёт в репозиторий.

> Заведите **отдельный** ящик только под оповещения и включите для него пароль приложения. Этот пароль знает каждый узел, поэтому рабочая почта сотрудника не подходит.

### Проверка

В `setup_app.py` на вкладке **Оповещения** нажмите **Отправить тестовое письмо**. Это стоит сделать обязательно: почти все ошибки настройки видны на первой попытке, а кнопка называет причину. Типичные ошибки: обычный пароль вместо пароля приложения, закрытый исходящий порт, адрес «От кого», который провайдер не принимает.

Консольный мастер спрашивает адреса одной строкой:

```bash
python setup_app.py --console
```

## Параметры

| Ключ | По умолчанию | Описание |
|---|---|---|
| `to` | `[]` | адреса; пустой список — ничего не отправляется, об этом один раз говорится в логе |
| `enabled` | `true` | выключает отправку целиком, не стирая адреса |
| `cooldown_minutes` | `60` | пауза после письма об одной неисправности |
| `digest_minutes` | `30` | как часто отправлять сводку обычных ошибок |
| `max_per_day` | `50` | потолок писем с узла за сутки; `0` — без ограничения |
| `disk_free_min_mb` | `5000` | порог свободного места; `0` — не следить |
| `log_tail_lines` | `50` | сколько строк лога прикладывать |
| `status_mail_minutes` | `0` | период [сводки по камерам](#регулярная-сводка); `0` — выключено |
| `daily_summary` | `""` | зарезервирован, сейчас не используется |
| `smtp` | нет | свой ящик узла, перекрывает `mail_account.json` |

Потолок `max_per_day` нужен потому, что ящик один на все камеры и суточная квота провайдера общая.

## О чём приходит письмо

Сразу, отдельным письмом:

- камера остановила себя после подряд идущих неудачных кадров;
- процесс завершился аварийно;
- процесс жив, но перестал публиковать статус;
- контроллер фильтров не отвечает или колесо не встаёт на место;
- камера не открылась при старте;
- сенсор не вышел на температуру;
- экспозиция не выдержана;
- заканчивается место на диске.

Остальные ошибки собираются в сводку раз в `digest_minutes`.

В письме: узел, экземпляр, тип камеры, имя машины и адрес, PID, время, строка ошибки, состояние камеры и последние строки лога.

Одна и та же неисправность не повторяется в течение `cooldown_minutes`. Повторы считаются, и их число попадает в сводку.

## Как это устроено

Работают два процесса.

**Камера** только кладёт письмо файлом в `~/.every_camera/outbox/`. Это быстро и без сети, поэтому почтовый сервер не может задержать измерение.

**`sentinel.py`** — отдельная служба, одна на машину. Она единственная открывает соединение с SMTP и замечает то, о чём упавший процесс сказать не может.

```bash
python sentinel.py                # обычный режим, раз в 15 секунд
python sentinel.py --once         # один проход, для проверки
python sentinel.py --interval 30  # другой период, секунд
python sentinel.py --config PATH  # другой файл конфигурации
```

- Письмо, положенное в очередь за секунду до гибели процесса, всё равно уйдёт.
- Гибель определяется по статус-файлу, за которым нет живого процесса, и отсутствию метки штатного завершения.
- Штатная остановка письма не даёт: Ctrl+C, `systemctl stop`, перезагрузка. Сторож сверяет идентификатор загрузки, поэтому шесть камер, исчезнувших разом, считаются одной перезагрузкой.
- Если SMTP недоступен, письма копятся в очереди и уходят позже. Письмо старше суток выбрасывается.

## Регулярная сводка

Наблюдатель за пределами сети камер не может достучаться внутрь, поэтому узел отчитывается сам. Раз в указанное число минут приходит одно письмо со всеми камерами машины:

```json
"alerts": { "to": ["ivanov@example.ru"], "status_mail_minutes": 30 }
```

```
Узел TORY (tory-asi), 2026-08-27T21:30:00

ASI_ASI           asi      running   кадров    412  ошибок    0  диск 41200 МБ  обновлён только что
JAPAN_1           japan    waiting   кадров     87  ошибок    2  диск 41200 МБ  обновлён только что
```

Проверить, не дожидаясь срока:

```bash
python sentinel.py --status-mail
```

## Установка службы

`systemd/install.sh` ставит сторожа вместе с первой камерой:

```bash
sudo systemd/install.sh asi
systemctl status every-camera-sentinel
journalctl -u every-camera-sentinel -f
```

Сторож запускается через `run.sh`, поэтому использует тот же интерпретатор из `env.sh`. На CentOS 7 это существенно: системный `python3` там 3.6. Запуск вручную тем же путём:

```bash
./run.sh --sentinel --once
```

У службы `Restart=always`. Если адресаты не заданы или файл отправителя не найден, сторож сообщает об этом в лог при запуске.

На Windows запускайте `run.cmd --sentinel`: см. [Windows](Install-Windows.md).
