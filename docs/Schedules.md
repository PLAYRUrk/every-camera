# Расписания

Формат расписания зависит от камеры:

| Камера | Откуда расписание |
|---|---|
| Canon, Infra | [файл интервалов](#файл-интервалов-canon-и-infra) |
| SPTT | не нужно: `capture_seconds` |
| Sentry | [`slots` в `config.json`](Camera-Sentry.md#слоты) |
| ASI, Japan | [слоты и режимы](#режимы-asi-и-japan) в `config.json` или файле |

Камера без расписания не падает, а поднимается в [режиме настройки](Setup-Mode.md).

## Файл интервалов (Canon и Infra)

Одна строка — один интервал измерений:

```
# Measurement Schedule
# Format: %Y-%m-%d %H:%M:%S - %Y-%m-%d %H:%M:%S

2026-03-08 12:00:00 - 2026-03-08 23:59:00
2026-03-09 08:00:00 - 2026-03-09 18:00:00
```

- Строки с `#` — комментарии.
- Камера снимает, только когда текущее время попадает в интервал. Вне интервалов статус — `waiting`.
- Файл может покрывать сколько угодно ночей вперёд.
- Сбой одного прохода у камеры Infra не останавливает поток: ошибка пишется в журнал, цикл выдерживает полсекунды и продолжает работу.

Файл можно рассчитать по углу Солнца: см. [Генератор расписания](Schedule-Generator.md).

## Режимы ASI и Japan

Режим задаётся ключом `mode`:

| Режим | Когда снимает | Что задаёт начало |
|---|---|---|
| `sun` | пока Солнце ниже `sun_max_angle` | заданные секунды каждой минуты |
| `time` | сразу или после Enter | цикл, фаза отсчитывается от `t_start` по местному времени |
| `sun_cycle` | пока Солнце ниже `sun_max_angle` | цикл запускается Солнцем, фаза привязана к `t_start` в UTC |

### sun

Слоты повторяются каждую минуту:

```json
{ "filter": 1, "exposure": 55, "seconds": [0, 30] }
```

| Поле | Описание |
|---|---|
| `filter` | позиция фильтра, 1–6 |
| `exposure` | экспозиция, с |
| `seconds` | секунды внутри минуты |

### time

Фаза отсчитывается от `t_start` по часам, а не от момента запуска. Если запустить измерения посреди ночи, кадры попадут в те же секунды, что и при запуске вовремя.

`t_start` наступает раз в сутки, и драйвер берёт ближайшее значение: если сегодняшнее дальше чем на 12 часов вперёд, опорной считается вчерашняя точка. Станция, поднявшаяся в 00:30 при `t_start = 22:00`, продолжит вчерашнюю ночь и не снимет лишние стартовые тёмные кадры.

`wait_for_enter` заставляет ждать Enter перед стартом. Без терминала (systemd, `nohup`) ключ игнорируется.

### sun_cycle

До достижения `sun_max_angle` камера не снимает ничего. Программа рассчитывает момент пересечения угла, отступает на время съёмки тёмных кадров и ждёт, чтобы они закончились к открытию окна. Цикл идёт до рассвета, затем снимаются закрывающие тёмные кадры. Следующей ночью всё повторяется.

**Фаза привязана к `t_start` в UTC.** Солнце решает, когда начать, а `t_start` — с какого слота. Ровно в `t_start` цикл приходит в нулевой слот.

Пример: период 1440 с, `t_start = 12:00` UTC, окно открылось в 11:37:10 UTC. До `t_start` остаётся 1370 с, значит, цикл сейчас на 70-й секунде. Первым снимается слот с ближайшей `delta` после 70 с, а в 12:00:00 начинается новый цикл со слота `delta = 0`.

Поэтому станции в разных точках и часовых поясах снимают один фильтр в одну секунду, если у них общие `t_start`, период и слоты. ASI и Japan в этом режиме синхронизируются между собой. При запуске в лог пишется:

```
Cycle phase locked to t_start 12:00:00 UTC (20:00:00 local), period 1440 s — first slot …
```

Без `t_start` цикл привязывается к первой целой минуте окна и с другими станциями не синхронизирован.

Необязательная [предварительная стадия](Intensity-Control.md#предварительная-стадия-preflight) открывает окно раньше, на более высокой уставке. Завершение на рассвете не меняется.

## Слоты циклических режимов

Слоты `time` и `sun_cycle` одинаковые:

```json
{ "delta": 100, "filter": 3, "exposure": 25, "binning": 1, "gain": 3, "readout": 5 }
```

| Поле | Описание | Ключ imagerd_rt |
|---|---|---|
| `delta` | смещение от начала цикла, с | `start_time`, мс |
| `filter` | позиция фильтра, 1–6 | `filter_num` |
| `exposure` | экспозиция, с | `exposure_len`, мс |
| `binning` | биннинг кадра; по умолчанию `camera.binning` | `binning` |
| `gain` | только ASI: усиление 1–3; пусто — `camera.gain` | `ccd_gain` |
| `readout` | считывание и поворот колеса после кадра, с | `prep_time`, мс |

У Hamamatsu нет аналогового усиления: слот с `gain` принимается, но драйвер сообщает, что ключ проигнорирован.

## Период цикла

Период берётся из `schedule_len`. Если он не задан (`null` или `0`), то вычисляется как `последняя delta + её экспозиция + её readout`, а при отсутствии `readout` — `dead_time`.

Примеры: расписание Тори даёт `1428 + 7 + 5 = 1440` с, а слоты `100;3;25;1` и `130;5;25;2` при `dead_time = 5` дают 160 с.

### Период в самом файле

Расписание и длина его цикла — одно целое, поэтому файл может назвать период сам, строкой `ключ = значение` в любом месте:

```
period = 1440
# delta(s);filter;exposure(s);binning
0;1;55;1
100;3;25;1
```

`period` — то же, что `schedule_len`. В `.json` ключ называется `schedule_len` и лежит рядом со `slots`. Значение из файла важнее значения из `config.json`.

Так же задаются `mode`, `sun_max_angle`, `t_start`, `dark_frames`, `dead_time`, а для ASI ещё `site_id` и `device_id`. У Japan последние два игнорируются. Неизвестный ключ не ломает файл: о нём сообщается, и слоты читаются дальше.

### Проверка периода по слотам

При запуске программа сравнивает период со слотами. Если пустой хвост цикла длиннее любого промежутка между слотами, выводится предупреждение в консоли и в GUI:

```
! japan: period = 1440 s, but the slots close the cycle at 720 s
  (Δ660 + 55 s exposure + 5 s dead time). The last 720 s of every cycle
  hold no slot, though its slots are never more than 60 s apart —
  one of the two numbers is not what was meant.
```

- Это важно: при ошибочном периоде камера может простаивать до `t_start`, и по ней не видно почему.
- Пауза в конце цикла сама по себе нормальна, предупреждение появляется, только если там поместился бы ещё один слот.
- Расписание из одного слота на цикл не проверяется.
- Если слоты не помещаются в период, сообщение выводится всегда.
- Период не исправляется автоматически: какое из двух чисел лишнее, знает оператор.

## Файлы расписания

`schedule_file` заменяет собой `schedule`.

### JSON

В репозитории есть готовое `schedules/asi_tory_1440.json` — расписание станции Тори: 36 слотов, цикл 1440 с.

```json
"asi": { "schedule_file": "schedules/asi_tory_1440.json" }
```

Соответствие ключей старого `schedule.conf`:

| imagerd_rt, мс | every-camera, с | Где |
|---|---|---|
| `zenith_angle_start` | `sun_max_angle` | глобально |
| `schedule_len` | `schedule_len` | глобально |
| `device ID` | `device_id` | глобально |
| `start_time` | `delta` | слот |
| `filter_num` | `filter` | слот |
| `exposure_len` | `exposure` | слот |
| `binning` | `binning` | слот |
| `ccd_gain` | `gain` | слот |
| `prep_time` | `readout` | слот |

Глобальные ключи файла (`mode`, `sun_max_angle`, `schedule_len`, `t_start`, `dark_frames`, `dead_time`, `site_id`, `device_id`) перекрывают одноимённые в `config.json`. Остальные ключи игнорируются. Файл может быть и просто списком слотов.

### Текстовый schedule.txt

Формат программ `asi-camera` и `japan-camera`. Строки с `#` и пустые строки пропускаются.

```
# режим sun: filter,exposure(s),seconds — секунды через двоеточие
1,55,0:30
2,55,15

# циклические режимы: delta;filter;exposure(s);binning;gain;readout(s)
100;3;25;1
1428;3;7;4;3;5
```

В циклической строке обязательны первые три поля. Без `binning` берётся значение камеры, без `gain` — общее усиление, без `readout` — `dead_time`. Поле можно оставить пустым: `0;3;25;1;;5` задаёт `readout` без `gain`.

Примеры лежат в `schedules/`: `asi_tory_1440.txt`, `japan_uzur_600.txt`.
